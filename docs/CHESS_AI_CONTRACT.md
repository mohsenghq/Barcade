# CHESS_AI_CONTRACT.md — Network format v1 (`az119`)

**Status:** v1 · **Source of truth:** this repo (RL_game_train). The app mirrors
this file at `mini_games/docs/CHESS_AI_CONTRACT.md` — keep them identical.
**Enforcement:** golden fixtures (FEN → tensor + policy mapping) committed into
the app's tests. This document is **load-bearing**: no encoder or training code
may be written until both sides agree on it.

## Overview

The app runs MCTS against a policy + value network served by `flutter_onnxruntime`
(masicai fork) 1.8.3. The network:

- **Input:** 8×8×119 binary planes (`input_shape = [1, 119, 8, 8]`, NCHW), from
  the **side-to-move's** perspective (Black positions are 180° rotated).
- **Policy head:** 8×8×73 = **4,672** logits (`policy_shape = [1, 8, 8, 73]`),
  illegal moves masked before softmax at MCTS time.
- **Value head:** scalar, tanh ∈ [-1, 1] (`value_shape = [1, 1]`), 1 = side-to-move
  wins.

Reference: AlphaZero chess, arXiv:1712.01815, Table S1 (input) + methods (policy).
We deliberately use the AlphaZero 119-plane layout, **not** LC0's 112-plane format
(GPLv3 — would contaminate the MIT app).

## Input planes (119)

### History planes (8 × 14 = 112)

For each of the last 8 positions (t-7 … t, oldest first; positions before game
start repeat the starting position or are filled by repetition):

14 planes per step:

| Index | Contents |
|---|---|
| 0-5   | Own pieces: pawn, knight, bishop, rook, queen, king |
| 6-11  | Opponent pieces: pawn, knight, bishop, rook, queen, king |
| 12    | Repetition: 1 if this position has occurred exactly once before |
| 13    | Repetition: 1 if this position has occurred twice or more before |

### Auxiliary planes (7) — all 8×8 filled with the stated value

| Index | Contents |
|---|---|
| 112-115 | Castling rights: white kingside, white queenside, black kingside, black queenside |
| 116    | En passant: 1 if an en passant square exists (file-specific plane, single bit) |
| 117    | Rule-50 counter: 1 while the halfmove clock < 50 |
| 118    | Colour (side to move): all 1s if white to move, all 0s if black |

**The exact plane ordering above is normative.** If it ever differs from the
implemented encoder, the encoder is wrong — fix the encoder and regenerate
fixtures.

## Policy head (8×8×73 → 4,672)

For each of the 64 squares, 73 moves. Within a square:

| Range | Meaning |
|---|---|
| 0-55 | Queen-like moves: 8 compass directions × 7 distances (0-7 for the first 7, since distance 8 on an 8x8 board never fully exists — see table below) |
| 56-63 | Knight moves (8 offsets) |
| 64-72 | Underpromotions: 3 pieces (knight, bishop, rook) × 3 destinations (left, straight, right) — used only for 7th-rank pawn moves |

Concrete direction table for the 8×8/queen-like block (rows 0-55):

| Row block | Direction (row, col deltas) |
|---|---|
| 0-6   | (0, 1)   right |
| 7-13  | (1, 1)   down-right |
| 14-20 | (1, 0)   down |
| 21-27 | (1, -1)  down-left |
| 28-34 | (0, -1)  left |
| 35-41 | (-1, -1) up-left |
| 42-48 | (-1, 0)  up |
| 49-55 | (-1, 1)  up-right |

(56 queen moves of length 1-7; on an 8×8 board the 8th is never on-board so the
block is 8×7 = 56.)

Knight offsets (56-63): the 8 standard L-shapes. Underpromotions (64-72): for a
pawn on rank 7 moving to rank 8, (knight, bishop, rook) × (file-1, file, file+1)
in that order.

**The authoritative policy index table is generated by `src/net/policy.py` and
locked by the golden fixtures.** If the mapping differs between trainer and app,
the app's MCTS will mask illegal moves incorrectly — the fixtures exist to catch
exactly this.

## ONNX graph contract

- `chess_net.onnx`, **fp32**, opset **17**, IR **8**, NCHW inputs.
- Ops restricted to: Conv, BatchNormalization (fused), ReLU, Add, MatMul,
  Softmax, Transpose — nothing exotic, so the app's bundled ONNX Runtime
  (1.23.0 via flutter_onnxruntime 1.8.3) runs it on every platform.
- Input names: `input` (float32 `[1,119,8,8]`).
- Output names: `policy_logits` (float32 `[1,8,8,73]`), `value` (float32 `[1,1]`).
- On-device artifact is the **int8 static-quantized** (QDQ / S8S8) build (~4×
  smaller); fp16 is the fallback for GPU execution providers. Strength must be
  re-verified after quantization (naive PTQ can cost Elo on the value head).

## manifest.json (sidecar, ships next to the .onnx)

```json
{
  "schema_version": "1",
  "network_format_version": "az119/v1",
  "input_shape": [1, 119, 8, 8],
  "policy_shape": [1, 8, 8, 73],
  "value_shape": [1, 1],
  "history": 8,
  "opset": 17,
  "onnx_version": "1.x.y",
  "torch_version": "2.13.0+cu126",
  "trainer_git_sha": "<full commit sha>",
  "model_sha256": "<sha256 of chess_net.onnx>"
}
```

Rules:

- `schema_version` bumps when the manifest *structure* changes.
- `network_format_version` bumps **only** when the encoder changes (plane layout
  or policy index mapping). It is a compile-time constant in the app
  (`expectedNetworkFormatVersion`); the app refuses to run on mismatch.
- `model_sha256` changes every retrain (informational + integrity).
- **Never put versioning in ONNX `metadata_props`** — flutter_onnxruntime cannot
  read model metadata on iOS/web.

## Golden fixtures (anti-drift)

The trainer's `src/data/fixtures.py` emits, for a fixed set of FENs:

1. The expected 119-plane tensor (raw bytes, NCHW).
2. The legal-move list.
3. The policy index mapping for each legal move (which of the 4,672 slots).

These are committed into the app's `test/` directory. The app tests:

- byte-identical tensor construction, and
- a run-the-real-net test asserting the argmax is a legal move.

Regenerate fixtures **whenever the encoder changes** — never edit them by hand in
the app.

## Release flow

1. Net passes the eval gate (candidate beats champion + fixed baseline).
2. Tag `net-v*` on this repo's GitHub Release, attaching `chess_net.onnx`
   (int8) + `manifest.json` + fp32 source.
3. The app pins URL + `model_sha256`, fetches into gitignored `assets/ai/`.
4. Future online handshake carries `network_format_version` + `model_sha256` so
   both peers validate the same encoding before a match.
